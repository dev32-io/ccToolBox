# v1.7.1 cross-skill refactor postmortem

> Originally documented in [CHANGELOG.md](../CHANGELOG.md) under v1.7.1.
> Sister writeups: [`skill-distill.md`](skill-distill.md), [`ui-refinement.md`](ui-refinement.md).

v1.7.1 was the refactor I should have done at v1.6 but didn't. Both `ui-refinement` and `skill-distill` had grown role-play persona files ("you are a senior designer," "you are a frustrated power user," "you are a senior engineer writing internal team documentation") that didn't outperform the simpler instruction-driven versions. Subagent dispatch was sequential where it should have been parallel: `ui-refinement` Phase 4.2 ran two critique passes one after the other in main context, and `skill-distill` Phases 2.1 and 2.3 each waited for the other to finish before starting. Phase 4.1 of `ui-refinement` was running a static screenshot scan when it should have been exploring the app like a real user. It captured the default state, formed an opinion, and called it done. This is the postmortem of all three at once.

---

## What changed

> All file:line references below are relative to `plugins/devTools/`.

### Persona files: role-play to instruction-driven

Three persona files shipped with role-play openings in v1.6.0 / v1.7.0. The diff for all three landed in commit `15c4841`.

**Before (v1.6 `skills/ui-refinement/personas/senior-designer.md:1-5`):**

```markdown
# Senior-designer critique persona

> Adopt this voice for every Phase 4.2 critique pass. You are a senior
> product designer doing a final visual review before the design ships.
> You've reviewed thousands of UIs and you can name what's off in one
> sentence. You don't lecture; you point.
```

**After (v1.7.1 `skills/ui-refinement/personas/senior-designer.md:1-6`):**

```markdown
# Visual-quality critique guide

Use this guide for one of the two critique passes in Phase 4.2. The
goal: surface every defect that would prevent shipping at a senior
visual bar. No role-play, no "imagine you are..." — just apply the
rules below to the captured screenshot.
```

**Before (v1.6 `skills/ui-refinement/personas/ruthless-tester.md:1-7`):**

```markdown
# Ruthless-tester critique persona

> Adopt this voice for every Phase 4.2 critique pass, **after** the
> senior-designer pass. You are a frustrated power user who has been
> stuck in this app for an hour. You hit every edge case. You want to
> find what the senior designer missed. The user-listed defects are a
> seed, not a cap — your job is to find more.
```

**After (v1.7.1 `skills/ui-refinement/personas/ruthless-tester.md:1-5`):**

```markdown
# Edge-state critique guide

Use this guide for the second critique pass in Phase 4.2 — the one
that hunts for what the visual-quality pass missed. Not role-play; a
state-coverage discipline.
```

**Before (v1.7.0 `skills/skill-distill/personas/skill-author.md:1-6`):**

```markdown
# Skill-author persona

> Adopt this voice when drafting SKILL.md and supporting docs. You are
> a senior engineer writing internal team documentation. Terse,
> opinionated, pattern-first. You have shipped skills before; you know
> the failure modes; you don't pad.
```

**After (v1.7.1 `skills/skill-distill/personas/skill-author.md:1-3`):**

```markdown
# Skill-writing rules

Apply these rules when drafting `SKILL.md` and supporting docs. Not
role-play — a fixed style + structure contract.
```

The content stayed: scan order, mantras, finding format, voice rules. The framing changed from "adopt this voice / you are X" to imperative rules and named constraints. The persona file is still the "lens" abstraction in the skill's file tree; what changed was the first 4-6 lines of each file.

Why role-play underperformed: the model doesn't treat persona descriptions as behavioral contracts. "You are a frustrated power user" reads as flavor. It registers, shapes tone for a sentence or two, and then fades. The model falls back to its default behavior. For critique tasks that means generic UI commentary ("this might feel a bit cramped") rather than the state-coverage discipline the persona was supposed to enforce. In test runs with the role-play framing, the edge-state critique drifted back to visual polish observations within two or three findings. The scan order from `senior-designer.md` wasn't being walked because "you are a senior designer" doesn't constrain scan order. It's an identity statement, not a procedure.

Explicit imperatives are different. "Walk the screenshot in this fixed order: 1. Hierarchy. 2. Alignment. 3. Spacing rhythm..." is a procedure. The model applies it. "Do not write hedged findings" is a rule. The finding-format examples (bad: "the spacing might be a little tight"; good: "list gap is 24px, mobile rule, reduce to 14px") are executable. In the instruction-driven version, every critique output had the required What/Where/Why/Severity fields. In the role-play version, findings were inconsistently formatted and consistently hedged.

The symptom: with role-play framing, the ruthless-tester critique produced 3-5 findings per pass, most of them visual (already covered by the senior-designer pass), with inconsistent format. With the instruction-driven version: 5-8 findings per pass, clearly sorted by edge-state category, all four fields present. The mandate "find at least N more defects than the user listed" landed because it's a concrete rule, not a character motivation.

### Subagent dispatch: sequential to parallel

**v1.6 shape, `ui-refinement` Phase 4.2 (single-agent, sequential):**

```markdown
### 4.2 — Critique through TWO personas

**Mandatory two-pass critique.** Read both:

- `personas/senior-designer.md` — alignment, sizing consistency, spacing
  rhythm, hierarchy, motion sense, density. The "would I ship this?" bar.
- `personas/ruthless-tester.md` — find what the user listed AND find
  what they missed. Edge cases (very short / very long content, error
  states, tap-target sizes, keyboard-open height, scroll boundaries).

Read `checklists/visual-critique.md` once and run the checklist on each
captured screenshot. For each finding, write:
...

Output the findings as a table. Don't classify into fixes yet.
```

**v1.7.1 shape, `ui-refinement` Phase 4.2 (`skills/ui-refinement/SKILL.md:289-296`):**

```markdown
### 4.2 — Two parallel critique subagents

**Dispatch two `Agent` subagents in parallel** (single message, two
`Agent` tool calls — `subagent_type: "general-purpose"`). Each gets
the captured screenshot path(s), the design-system guardrail from
Phase 1, and one critique guide. They return findings tables; the
main agent merges and dedupes.
```

**v1.7.0 shape, `skill-distill` Phases 2.1 and 2.3 (sequential, main context):**

```markdown
### 2.1 — Prior art

`WebSearch` for how others have built / framed this kind of skill.
[...reads sources in main context...]

### 2.3 — Destination conventions

Don't ask the user yet — research first so Phase 4 can present an
informed recommendation.

Read `references/destination-conventions.md` and gather:
[...probes filesystem in main context...]
```

**v1.7.1 shape, `skill-distill` Phases 2.1 and 2.3 (`skills/skill-distill/SKILL.md:143-148`):**

```markdown
**Dispatch 2.1 and 2.3 as parallel subagents** (single message, two
`Agent` tool calls — `subagent_type: "general-purpose"`). They are
independent: one does web research, the other inspects the local
filesystem. Phase 2.2 stays in the main agent because the format
rules need to be loaded for Phase 3 anyway.
```

Why parallel: the two passes in `ui-refinement` Phase 4.2 are independent. Visual-quality critique and edge-state critique don't share working state. Subagent A has the screenshots and the `senior-designer.md` rules; Subagent B has the same screenshots and the `ruthless-tester.md` rules. Neither needs the other's output to run. Serializing them burns wall-clock and loads both pass contexts into the main agent, which accumulates over a 5-7 pass loop. By the third iteration, the main context carries six full findings tables, twelve sets of subagent outputs, and fix descriptions for every pass. Running the subagents in parallel means the main agent receives only the merged table from each pass, not the full working context of each subagent. The `ui-refinement` CHANGELOG entry states this directly: "Keeps the main context lean over long iteration loops; speeds up each pass."

The same logic applies in `skill-distill`: the prior-art search (web I/O) and destination probe (filesystem I/O) are fully independent. The web search doesn't need to know where the skill will land. The filesystem probe doesn't need prior-art results to inspect `~/.claude/` paths. Running them sequentially gained nothing except the guarantee that 2.3 ran in a slightly fuller main context, which was the wrong direction. The parallel dispatch dropped both into isolated subagent contexts, let them run concurrently, and merged their outputs into Phase 3.

### Phase 4.1: static screenshot to aggressive exploration

**v1.6 instruction, `ui-refinement` Phase 4.1 (before `15c4841`):**

```markdown
### 4.1 — Capture baseline

Set the viewport (per platform's `browser_resize`-equivalent), navigate
to the target screen, drive any required state (login, fixture data,
trigger the UI state — empty / streaming / error / etc.), and capture
both:

- A screenshot (for visual critique)
- An accessibility snapshot or DOM inspection (for measurements:
  bounding boxes, computed styles, font sizes)

Save each baseline screenshot with a deterministic name
(`<scope>-<viewport>-<scenario>-baseline.png`) in the project's existing
screenshot dir if any, otherwise the playwright MCP default
(`.playwright-mcp/`).
...
```

**v1.7.1 instruction, `skills/ui-refinement/SKILL.md:247-286` (after `15c4841`):**

```markdown
### 4.1 — Aggressive exploration + baseline capture

This step is **not** "open the page and screenshot it." It is
"actively use the feature like a ruthless power user, click into
every corner, and capture every state you find."

...

- **Click every interactive element you can see** — buttons, menus,
  icons, tabs, chips, three-dot menus. Capture each open / hover /
  focused state as a separate scenario.
- **Open every entrance and exit every exit** — modals, drawers,
  tooltips, popovers; close via button, ESC, click-outside, back.
- **Try every input** — empty, whitespace, oversized paste, emoji,
  RTL, rapid-fire, mid-flight cancel.
- **Walk the full flow end-to-end** — first-run → typical use →
  edge → exit. Don't stop at the visible screen.
- **Scroll everywhere** — top, mid, past-end. Sticky headers.
  Nested scroll containers.

The bar for finishing 4.1: you can no longer think of a fresh
interaction to try in this scope. If you stopped earlier than that,
go back.
```

The static capture instruction ("navigate to the target screen, drive any required state, capture both") was accurate as far as it went. It just didn't go far enough. The result: the critique subagents received one or two screenshots of the default happy-path state and produced findings that were exclusively visual-polish findings. Broken click handlers, modal trap states, error UI rendering, form submission paths, and behavior on oversized content were never captured because they were never triggered.

The aggressive exploration mandate is the fix for a class of bugs the visual-quality pass structurally cannot find: things that only exist in states you have to create. "The modal traps keyboard focus" requires opening the modal. "The error banner overlaps the submit button" requires triggering an error. "The list performance degrades with 50 items" requires loading 50 items. Screenshotting the default state before critique is the wrong order of operations. Explore the full state space first; then critique what you find.

The new title for Phase 4.1, "Aggressive exploration + baseline capture," signals the expansion. The addition to `SKILL.md:58-66` names the anti-pattern: "passive exploration," defined as screenshotting the default state and calling it done. Naming the anti-pattern alongside the mandate is the pattern from the other skills: show the wrong shape explicitly so the model has something to check against.

## Tradeoffs and hard parts

### Why one combined refactor, not three separate ones

The three changes are coupled in a way that made separate releases the wrong call.

Instruction-driven personas produce more findings per pass: consistent format, proper category breakdown, explicit state coverage. That's the point. But more findings per subagent means more content returned to the main agent per pass. If Phase 4.2 still ran sequentially in the main context, the context pressure per pass would have gotten worse, not better. The persona rewrite needed the parallel dispatch to stay manageable across a 5-7 pass loop. Shipping the persona rewrite without the dispatch change would have produced a regression in long-loop behavior.

Similarly, the aggressive exploration mandate in Phase 4.1 produces more screenshots per pass: more distinct states, more edge cases captured. That means Subagent B (edge-state critique) has more material to work from. If Phase 4.1 had been updated but Phase 4.2 had stayed sequential, the extra material would have landed in a main-context run and created exactly the context-pressure problem the parallel dispatch was designed to prevent. All three changes point in the same direction: more thoroughness per pass, kept lean by parallel isolation.

The rejected alternative was three sequential PRs: persona rewrite first (observe behavior), then dispatch, then exploration mandate. That would have required three rounds of testing the same loop with different shapes and introduced a window where the persona rewrite was live but the parallel dispatch wasn't. The intermediate state would have been actively worse than v1.6.

### Why keep the persona file naming, not flatten to role.md

The files are now called "Visual-quality critique guide" and "Edge-state critique guide" internally, but the directory paths are still `personas/senior-designer.md` and `personas/ruthless-tester.md`. The rejected alternative was renaming the files to match their new titles: `personas/visual-quality-guide.md`, `personas/edge-state-guide.md`.

The persona file is still the "lens" abstraction in the skill's file tree. `SKILL.md` references it as the source of the critique rules for one of the two subagents. The path appears in subagent handoff instructions, in the `## Files in this skill` section, and in cross-references from `ui-refinement.md`. Renaming the files would have changed every reference, updated no behavior, and obscured the historical continuity of the files (the content is mostly the same; the framing changed).

More importantly: the distinction between "what the file is named" and "how it opens" is the entire point of the v1.7.1 change. The file is a lens; the opening of the file was changed from role-play framing to instruction-driven rules. Renaming the file to match its new opening would conflate the abstraction (a lens on critique behavior) with the implementation detail (whether the opening line says "you are" or "use these rules"). The lens abstraction is correct. The prior implementation of the lens was wrong. Keep the abstraction; fix the implementation.

### Why apply to both skills simultaneously, not iterate on one first

`ui-refinement` and `skill-distill` shipped in the same release window (v1.6.0 on May 4, v1.7.0 on May 4). The rejected alternative was refactoring `ui-refinement` persona files first, observing behavior for a few sessions, and then porting the pattern to `skill-distill`.

The problem: `skill-distill`'s persona file (`skill-author.md`) and its subagent structure were being written at the same time the v1.7.1 decision was being made. If I'd waited for `ui-refinement` testing to finish, `skill-distill` would have been authored against the role-play pattern. A subsequent refactor would have been correcting a known-wrong pattern that was copied from a file I'd already decided to fix. The core lesson (role-play is noise, rules are signal) is general enough that it doesn't need per-skill validation. The evidence from `ui-refinement` test runs was sufficient to apply it to `skill-distill` immediately.

There's also a maintenance argument: two skills using different persona file conventions would have required a decision at every future skill: is this one role-play or instruction-driven? The answer is always instruction-driven. Making it consistent across both skills in one release closes that decision and establishes the convention for any future skill that ships persona files.

## What's next

Three open questions from the v1.7.1 refactor remain unresolved.

Whether the same pattern applies to `retro`. The `retro` skill currently runs a single-subagent analysis pass and does not use persona files. The v1.7.1 changes don't touch it. But `retro` has a subagent that reads a full session diff and commit history, which is the same large-context problem that motivated Phase 1.2's subagent dispatch in `skill-distill`. If `retro`'s analysis subagent is being asked to hold both the diff and the analysis framework in the same context, there's a version of the parallel-dispatch pattern that would apply: one subagent for the diff read, one for the knowledge-base check, merged before the output pass. This hasn't been tested. It's a candidate for v1.7.2 if `retro` sessions start showing context-pressure symptoms.

Whether persona files should be promoted to a shared library across skills. `senior-designer.md` and `ruthless-tester.md` are currently owned by `ui-refinement`. If a future skill needs visual-quality critique behavior, it would either copy the files or reference them across skill boundaries, neither of which is clean. A shared `personas/` library at the plugin level would let skills reference the same guides without duplication. The obstacle: Claude Code's skill loading reads files relative to `SKILL.md`'s location; cross-skill paths aren't currently supported. A shared library would require either a loader change or a convention for symlinking, and neither exists yet.

Whether the design-system guardrail in `ui-refinement` should adopt the same instruction-driven shape. The guardrail is currently produced during Phase 1.3 as a user-authored brief, not a pre-written document. The user signs off on it and it's carried forward as a named constraint in every subsequent phase. That's already instruction-driven: it's a rules document, not a persona. But the Phase 1.3 instructions that produce it are still partially framed as "write a brief that includes..." rather than a fixed template with named fields. Tightening Phase 1.3 to produce a structured guardrail (fields: tokens to preserve, patterns to protect, escalation threshold) would make the guardrail more consistent across runs and easier to reference in subagent handoffs. That change is deferred; the current free-text brief works for the sessions tested so far.
